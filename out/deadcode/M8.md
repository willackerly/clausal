# M8: the dead-code report as a tool, run on three projects

Plan node M8, 2026-11-10; corrected and partly rerun on 2026-11-11 after an independent review (`tools/deadcode/review/`, summary in "After the review" below). Tool: `tools/deadcode/` (README there). Per-project reports: `out/deadcode/{ns,pfr,carleson}/REPORT.md`. Side-by-side table: `out/deadcode/COMPARE.md`. Working copies: `corpora/<project>_trim/m8/` (git-ignored). The three built corpora were not modified.

## Result

**The one-off analysis is now a tool that runs unchanged on Lean 4.34 and 4.36, and on all three projects the roots still compile with the same axioms after everything the tool could cut was deleted.** Against the node's target (runs on a second and third project, deletions confirmed by build): it runs on all three, and the deletions are confirmed by building the root modules and then the projects' other build targets (Lake's default targets; for `carleson` also the comparator `Challenge` and `Solution` libraries). The first version built only the root modules for `pfr` and `carleson` and left their comparator files broken; the review found that, the tool was changed and both runs were repeated. The node is exploratory under the plan's rule 1: the scope rule, the outward-command rule, the trace tightening and the other-targets step were added after earlier runs, and no commit freezes them.

## The tool

- **Input**: a built project and roots (names, a file, a blueprint's `\lean{}` tags, or all theorems of named modules). **Output**: `analysis.json`, `unreachable.jsonl` (one line per unreachable declaration with class, reasons, role), `modules.json`, `clones.json`, `REPORT.md`.
- **Declarations, dependencies and tables are read from Lean**: the built environment (term dependencies, simp sets, instance table, reducibility, `ext` table, unexpanders), Lean's parser on each declaration head (attributes, keyword), Lean's declaration ranges, and the `.ilean` reference index (names used in source, inside and outside declarations). Source text is cut at Lean's ranges.
- **Text or a hand-written list decides in five places** (README, "What is read, and from where"): a list of 31 attribute names that do not hold a declaration back; the first word of commands outside declarations, which decides whether an emptied file may go; `… in` lines above a declaration; name tests for auto-generated constants in the exporter; and identifiers in the error text or on the failing source line when Lean's messages and traces do not name the cause (30 `ns` restorations).
- **The term graph is checked against the kernel.** `check` walks the unfolded constant closure of the roots and compares: equal on all three projects (37,067, 847 and 2,635 declarations). This holds once shared `_proof_N` auxiliaries are counted with the declaration that uses them: the kernel closure also reaches 183 (`ns`) and 4 (`carleson`) auxiliary proofs named after an unreachable declaration, because Lean reuses identical proof terms. The reviewer checked that those declarations (91 in `ns`, 3 in `carleson`) were deleted where they could be cut (91 of 91, 2 of 3) with the builds passing. The first version of the exporter missed 3 `carleson` declarations; the check found them.
- **Safe delete** copies the project, deletes, rebuilds the root modules, traces each failure to deleted declarations (error message; Lean's simp and instance traces of the original file; bisection), restores them and repeats. When the roots build it builds the project's other targets (default targets and the `extraTargets` of the project file) the same way; what those need is restored and counted separately, because the roots do not need it. Then it compares axioms. `--confirm` re-deletes each restored declaration alone.
- **Version tolerance**: the three Lean files import only `Lean` and run with `lean --run` under the inspected project's toolchain. No change was needed between 4.34.0-rc2 and 4.36.0-rc1/rc2, including `carleson`'s use of the module system. One version difference was missed in the first version and found by the reviewer: on 4.36, `importModules` does not refuse two project modules that declare the same name. It keeps one constant and says nothing. The `pfr` export therefore lacks the six public theorems of `PFRPalomar/Solution.lean` (same names as in `PFRPalomar/Challenge.lean`), and the `carleson` export lacks two anonymous `local instance : Fact (0 < 2 * π)` whose generated names clash. The exporter now reads each module's own `.olean` again and lists every such name (`export/clashes.json`, 0 in `ns`). The lost declarations are in no count; their modules are never deleted, their text is never cut, and what their text names is held.

- The two clean builds of a project were started together, so they saw the same load; the absolute values are several times the quiet-machine ones and only the ratio means anything.
- The `ns` rounds 4 and 5 were interrupted and resumed, so their times are lower bounds.
- **The two `pfr` pairs timed the same sources** (the review changed nothing inside the import closure of the `pfr` roots) and gave −2.1% and −4.2%. One pair of builds on a shared machine is therefore good to about two points; for `carleson` the trimmed sources differ between the pairs by three definitions.
- **The saving is much smaller than the share of lines deleted.** The one-off estimated −17% to −21% for `ns` against the whole project (2,657 files); measured on the import closure of the two headline modules it is −6.3%, where 20.2% of the closure's lines were deleted (26.2% is the whole-project figure). - Bisection is the expensive step: 27 of the `pfr` run's builds were bisection steps.

| used only by other unreachable declarations | 9,009 (58%) | 102 (38%) | 166 (29%) |
| unreachable with a needed twin statement | 859 (5.6%) | 4 (1.5%) | 7 (1.2%) |
| … the same with headline roots (reviewer, see below) | | 117 of 300 (39%) | 423 of 857 (49%) |
| files that mix needed and unneeded declarations | 1,311 of 2,657 (49%) | 35 of 76 (46%) | 78 of 124 (63%) |
| wholly unreachable modules | 301 of 2,657 (11.3%) | 7 of 76 | 11 of 124 |
| near-identical module pairs | 15 | 0 | 0 |

- **The shares of unneeded declarations are of the same order** (18% to 29%), but the roots differ: four theorems for `ns`, every blueprint-tagged declaration for the other two. The reviewer measured the human projects with headline roots instead (exploratory; roots chosen by the reviewer from each project's comparator file or README): for `pfr`, the six library theorems that `PFRPalomar/Solution.lean` applies; for `carleson`, `classical_carleson`, `metric_carleson` and `linearized_metric_carleson`. `analyze` gives 300 of 1,118 unreachable (26.8%, 12.2% of lines) for `pfr` and 857 of 3,201 (26.8%, 19.2% of lines) for `carleson`, against 29.4% (24.6% of lines) for `ns`. Term graph only; no build was run on these root sets (`tools/deadcode/review/out/{pfr,carleson}_headline/`).
- **Where the unneeded material sits differs.** In the two human projects it is mostly in directories whose names say it is headed elsewhere, and the main development is 93% to 98% needed. `ns` has no such directories. Files that mix needed and unneeded declarations are common in all three (`ns` 1,311 of 2,657, `pfr` 35 of 76, `carleson` 78 of 124), so mixing within a file does not separate the projects.
- **Chains differ.** In `ns` 58% of the unneeded declarations exist only to support other unneeded ones; in the human projects 29% to 38%. With headline roots the human figures rise to 39% (`pfr`) and 49% (`carleson`). Near-identical module pairs occur only in `ns` (15). Wholly unreachable modules occur in all three (`ns` 301 modules with 4,147 declarations, `pfr` 7 with 17, `carleson` 11 with 23).
- **Unneeded declarations are shorter in the human projects** (9% of lines for 18% to 24% of declarations; the builder's reading: mostly short API lemmas). In `ns` they are closer to average length (24.6% of lines for 29.4% of declarations).
- **Elaboration-time dependencies differ in kind between the projects.** Lemmas named in `simp` / `rw` calls but absent from the term occur in all three (177, 1, 7). `@[simp] … := rfl` lemmas used by a bare `simp` occur only in `ns` (17). Coercion instances occur in `ns` (5) and `carleson` (6). The project's own tactic code and a `positivity` extension occur only in `pfr` (9). Within class 2-attribute the rates overlap (`ns` 22 of 1,120, `pfr` 2 of 61, `carleson` 6 of 137; intervals overlapping).

### What cannot be concluded from one machine project

- **Not that machine-written Lean has more dead code than human-written Lean.** One corpus, one generating system, one problem; and the roots are not comparable (4 against about 240).
- **Not why the unneeded material exists.** "Superseded", "abandoned branch" or "exploration" are readings of names and file headers. The tool measures need, not intent.
- **Not that the staging directories are waste.** They are unneeded for the blueprint's statements and are the part of the human projects meant for Mathlib.
- **Not a rate for other projects.** The intervals above are a guide for declarations in a project like the one measured; why `ns` has 22 such cases was not measured.
- **Nothing about mathematical quality.** No one rated quality. Descriptions of what declarations are, as opposed to counts, are the builder's readings of names and source (a model reader, not evidence): theorems packaged as definitions, an instance shortcut, repetition rather than copies, short API lemmas, positivity and measurability facts.

## Limits

- **Roots decide everything.** A blueprint tags statements someone chose to tag; `carleson`'s Carleson–Hunt file is "unneeded" only in that sense.
- **A project's other deliverables survive only because their targets are built.** The comparator statements of `pfr` and `carleson` are unreachable from the blueprint tags. They stay in the trimmed copies because the tool now builds the default and extra targets and restores what they need. A file that no listed target builds has no such protection. For `ns` both runs predate this step: the default targets were built once on each final state, and they build.
- **Declarations lost to a name clash are not analysed** (6 in `pfr`, 2 in `carleson`). They are kept, with their modules, and counted nowhere. Leaving the other module out (`excludeModules`) would bring them into the analysis; that was not done, so that the `pfr` figures stay comparable with the reviewed ones.
- **Restored-as-dependency declarations were not tested one by one** (44 in `ns`, 18 in `pfr`, 1 in `carleson`).
- **Trace attribution names every deleted simp lemma or instance the original elaboration used in the failing declarations.** `--confirm` was run for `pfr` and `carleson` (all 26 hidden dependencies and all 7 comparator restorations that can be cut alone confirmed). For the `ns` `held` run the reviewer ran the first confirmation stage on a clean rebuild: each of the 22 was deleted alone and the blamed module rebuilt, and all 22 fail again. The 222 new restorations of the `ns` `term` run were not confirmed; its 11 over-restorations show the step can err towards restoring too much.
- **One result file was edited by hand after its run.** `ns/runs/term/result.json`: notes and the 11 withdrawals were added, the counts changed from 255 restored and 15,125 deleted to 244 and 15,146, and round 33 was replaced; the run's own record is `result_before_cleanup.json`. The reviewer's clean rebuild of the final `ns` state builds with the same statements and axioms. The `carleson` result file of the first session also carried a hand-written note; it is superseded by the rerun, whose files are as the tool wrote them (the old ones are under `superseded/term_before_review/`).
- **Commands outside declarations are recognised by their first word**, on text outside Lean's ranges. This and the four other places listed under "The tool" are where text or a hand-written list decides something.
- **Exploratory.** Rules changed after runs (scope rule, outward-command rule, trace tightening, other-targets step, name-clash handling) and no commit freezes the tool; the `ns` runs were made before the last two changes and were not repeated (about three hours of builds).
- **Declarations Lean's `isInternalDetail` takes for auto-generated** and that have no parent are not source-level declarations for the tool; they are never deleted.
- **The trimmed projects were built, not re-audited**: the roots elaborate, pass the kernel during the build, and have the same axioms; the reviewer also compared the printed statements of every root before and after (identical). Comparator was not run.
- **Build-time figures are from a loaded machine.**

## After the review (2026-11-11)

An independent review (`tools/deadcode/review/`) reran the tool on all three projects, rebuilt the trimmed sources from clean, compared statements and axioms of every root with Lean's own `collectAxioms`, and confirmed the 22 `ns` restorations one by one. The kernel-level claims held. It found two defects and several overstated sentences. What was done:

| finding | what was done |
|---|---|
| The trimmed `pfr` and `carleson` no longer built their comparator files | `safe-delete` now builds the default and extra targets after the roots and restores what they need (`--roots-only` switches it off). `pfr` and `carleson` rerun from fresh copies: 179 and 540 deletions instead of 189 and 543; comparator files intact and building. Hidden dependencies of the roots unchanged (the same 10 and 16). |
| On Lean 4.36 the exporter silently lost declarations whose name another module also declares | The exporter lists them (`clashes.json`); the driver warns, keeps their modules and holds what their text names. `pfr` class 1 went from 130 to 126 (four helpers of `Solution.lean` are now class 2-command). |
| Comparisons the data do not support (mixed files, whole modules, "same kinds", build time against whole-project lines) | Corrected in place, with the reviewer's figures; the line share of the timed modules is now computed by the tool. |
| A guess about four roots on a human project | Replaced by the reviewer's measurement with headline roots. |
| Builder's readings presented as facts | Marked as readings. |
| Result files edited by hand | Stated under Limits; the `carleson` file is superseded by the rerun. |
| The `twin` field depended on Python's set order | Fixed (`sorted`); two runs of `analyze` now give identical files. |
| `ns` restorations not confirmed | The reviewer confirmed all 22 of the `held` run; stated above. |

Not done: the `ns` deletions were not repeated with the changed tool (about three hours of builds). For `ns` the changes make no difference to the analysis (no source-level name clash; `analysis.json` is unchanged apart from the tie-break order), and its default targets build on both final states.
