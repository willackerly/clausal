## 2. Defects in today's compiler that all three proposals must answer

### 2.1 Narrowed rules that are true of every operation compile, and nothing flags them

Kernel-checked in `vac/Vac.lean`:
- `Monotone op.successful v op.accepted` holds for every operation and every variation.
- The same holds for `op.rejected`.
- For a yes/no answer with acceptance meaning `= true` (as `L.said`, `clausal/lean/Ledger/Pieces.lean:72`), `IndependentOf op.successful v (fun ans _ => ans)` holds for every run function, and the `.rejected` version too.
- An operation that never answers satisfies `NeverChanges op.rejected m`.

The reason is `Op.HoldsAt2` (`clausal/lean/Frames/Core.lean:87-90`). Under narrowing it assumes both calls answered and both are of the narrowed kind, and the frame's content then follows from those assumptions alone.

These sentences compile today. Each one reads like a rule the repository marks as expected to be refuted (`probe_a.out`):

| Compiles to a statement true of any code | Reads like |
|---|---|
| "A successful transfer never loses acceptance when the amount is larger" → `Frames.Monotone (L.apply).successful L.largerAmount …` | `ledger_rules.feature:75`, `@expect-refuted` |
| "A successful transfer gives the same answer when the amount is larger" → `Frames.IndependentOf (L.apply).successful …` | `:101`, `@expect-refuted` |
| "A rejected transfer gives the same answer when only the amount differs" | `:94`, `@expect-refuted` |
| "A successful transfer never loses that it is rejected when the amount is smaller" | (contradiction hidden) |

- **Non-vacuity check.** The only non-vacuity theorem for a rule is `reading_sat`: the scope can be satisfied (`clausal/clausal/links.py:310-313`, reported at `clausal/clausal/report.py:376-392`). The scope here is `True`.
- **"COVERS NO CALL ON THE GRID".** This flag (`report.py:366-369`) fires only when no call of the narrowed kind occurs on the grid. Accepted transfers do occur, so it stays silent.
- **What follows.** By reading the code, not by running it, such a rule would get a proof that the reading holds, labelled non-vacuous.
- **Why it matters here.** Aliases row 8 and reshape R1 both make "accepted" the adjective. With that change, "An accepted transfer never loses acceptance when the amount is larger" compiles to the same vacuous term (`probe_accepted_adjective.out`). Reshape R2 refuses narrowing only for frames 4 to 8.
- **Needed first; this is my suggestion and is not built.** Refuse a narrowed rule when its reading holds for every `run` of the operation's types. A fixed tactic over `∀ run` would decide the cases above.

### 2.2 What is printed about coverage contradicts the Lean in two sentence shapes

These lines are what layers proposes to write into the `.feature` file.

**First shape: "For X, if it is accepted/rejected, …".**
- "For a lookup, if it is accepted, the result is the balance of the account in the ledger" compiles to `Frames.ResultIs (L.lookup).successful …`.
- The printed reading still says "every such call, accepted or rejected [default D2]" and "the call gives an answer [default D1]", and lists D1 and D2. In the same block it also prints "ONLY accepted calls are covered … no answer … outside" (`probe_b.out`).
- "For a successful lookup, …" gives the same Lean and is printed correctly. "For a transfer, if it is rejected, the ledger is unchanged" has the same fault (`probe_a.out`).
- Cause: `echo_rule` checks the clause-level `g["mods"]` (`clausal/clausal/vocab.py:1121-1130`, `:1151-1152`), but this form attaches the narrowing to the claim (`vocab.py:1014-1017`).

**Second shape: any narrowed two-run rule.**
- It prints "both must give an answer [default D10]" (`vocab.py:1146-1148`). Under narrowing, `HoldsAt2` requires no answer (`Core.lean:87-90`), and the executable reading allows silence too (`clausal/lean/Frames/Check.lean:38-42`, `silenceAllowed`).

**Unsigned text.** These lines are Python strings, and `defaults:` and `weakenings:` are top-level YAML keys. The sign-off digest hashes only `- id:` entries and the Lean definitions they name (`clausal/clausal/vreport.py:147-176`), so none of this text is under any signature.

### 2.3 More same-meaning pairs than any proposal lists, with different Lean text

- "A transfer is always accepted" → `Always L.apply (fun ans => (L.apply).accepted ans)`, but "For a transfer, it is accepted" → `Always L.apply (fun ans => L.said ans)` (`probe_c.out`).
- "never loses acceptance" and "never loses that it is accepted" differ in the same way (`probe_b.out`).
- The two are equal only after unfolding `Bdd.opMut` (`clausal/lean/Bdd/Ops.lean:34-36`) and `L.apply` (`Pieces.lean:109`). A duplicate report keyed on the term text misses them.
- The wallet pack has a third word for acceptance, "the operation succeeds" (`clausebook.yaml:231`). Reshape R1 does not mention it.

## 3. Aliases

**Verified as stated:** findings 1, 2 (now kernel-checked), 3, 5, 6 and 7. Finding 3 is incomplete (see 2.3). "Cannot drift" holds for the Lean term but not for what the report prints: the two forms in finding 3 give the same Lean and different printed coverage, one of them wrong (2.2).

**A1. Check 4 refuses the proposal's own aliases.**
- Count per word, and these fail: "is always rejected" against "is never accepted" (`vocab.py:1010`), "always succeeds" against "is always accepted" (`:1009`), and row 8's "successful" against "accepted".
- Row 9's canonical form contains "only if" and "every" while its alias contains neither, and "domain-word forms may contain none" contradicts "the same number as the canonical form".
- Count in total instead, and check 4 lets "always" and "never" swap freely.
- Either reading fails.

**A2. Check 3 deletes most of the existing aliases.** "the total of" and "the aggregate" are one piece in one position (`clausebook.yaml:592`), as are the four forms of `l.balances_of` (`:259`) and both hard-coded pairs. For the present Clausebook, "registered aliases" therefore comes to reshape R1. The proposal's real content is classes P, G, D and E.

**A3. Row 4 puts frame 16's condition where English reads narrowing.**
- The alias is "A transfer, if it is rejected, gives the same answer when the amount is larger."
- Its neighbour, "A rejected transfer gives the same answer when the amount is larger", compiles today and is vacuous (2.1).
- A reader who takes the alias as narrowing also drops the requirement that both calls answer when the first is accepted, which the Lean keeps (`Core.lean:86`).
- Check 5 passes, because the skeletons differ.

**A4. Fronted forms across ", and".**
- Apply row 5 to all of `ledger.feature:238`: "If a batch applied as a whole is rejected, it never changes the ledger, and a batch applied as a whole never changes the total of all balances of the ledger."
- `clause_splits` cuts at ", and" first (`vocab.py:1205-1217`), so the second clause covers every call. A reader carries the "If … rejected" over both.
- Rows 1 and 2 behave the same way with "When V, …, and …".
- These are the two error kinds proxy readers missed (`trials/sentences/RESULTS.md:92-93`). Check 7 tests that the parse is unique, not how a reader scopes the sentence.

**A5. Row 3 is not class G.**
- "the subject satisfies every {c} under its rule" wraps the predicate around the quantifier. It is not a form of `every` (`clausebook.yaml:613`), and its holes come from two pieces, so check 1 cannot hold. It is class C.
- The active voice also makes "the subject" the default referent of "its", which pulls "under its rule" toward the subject's rule.

**A6. Row 6, "Given that K, …".** "Given that" is factive in English: it presupposes K. Fronted `given` next to `if_then` brings back the frame-5 pair that differs only on calls outside K that give no answer (`clausal/lean/Frames/Lemmas.lean:47-77`). No check catches that.

**A7. Row 1's note is wrong.** It says forms starting "An accepted key release …" are refused by check 4. They are compositions, not aliases, so no alias check applies. With the row 8 change they compile to the vacuous term (2.1).

**A8. Class E is not an alias.**
- "every … is not P" against "no … is P" are compositions of two pieces each. The schema's `of: <piece id>` cannot express that.
- E changes the Lean term.
- When `fmt` rewrites an E form, the text in the file changes after someone reviewed it.
- Refuse "every X is not P" instead, as reshape does.

**A9. Class D hides content (row 9).** "the all-or-nothing replay of the batch" drops that the reference is the same crate's `apply_batch` (`clausebook.yaml:477-488`). That rule passes when both operations share a bug. Someone signing the alias signs a name, not its meaning.

**A10. Row 1, "refuted whatever its wording", is likely wrong.**
- Guarantee 4 is listed as not holding today because of D4, where only the first hierarchy value is read (`tdflite-ideas/TDFLite policy core formal verification plans.md:63`, `:180-186`).
- A variation of "entitlements appended at the end" would leave the first value alone, so on that reading the rule may pass on the present code. A variation of "superset in any order" refutes it.
- "Gains an entitlement" does not say which. This is reasoned from the notes, not checked against the Go code or the model.

**A11.** The duplicate report keyed on term text misses the definitional duplicates in 2.3.

**A12. The trial cannot license an alias.**
- The "Hurt" rule is a point-estimate threshold.
- Assume 5 trap kinds, 8 to 16 flipped judgements per kind per arm, and a true catch rate of 0.80 to 0.95 in both arms. Then it fires **41% to 90%** of the time with no real difference. Clustering by reader or item would raise this.
- "Helped" is unreachable by the proposal's own estimate.
- So a neutral alias is withdrawn more often than it is kept.

## 4. Reshape

**Verified:**
- R6 gives identical Lean on every current fixture (section 1).
- Seven frames do have both a verb-phrase form and a Then form (`clausebook.yaml:695-905`).
- No form accepts the words "accepted or rejected".

**B1. The R2 marker reads as excluding calls that give no answer.**
- In "A transfer, accepted or rejected, never changes the total …", a call that panics is neither accepted nor rejected, yet `.every` requires an answer (`Core.lean:73`). The marker pushes the no-answer trap toward the wrong verdict.
- Frame 1 is not exempted, so `wallet.feature:75` becomes "A withdrawal, accepted or rejected, always gives an answer", which presupposes what it asserts.
- This is stronger than the proposal's "D1 stays hidden": the marker states the weaker claim. Compare item 3 under "What to avoid" (`out/prior_art_vocabulary.md:310`).

**B2. One "If" with two behaviours.**
- "If a transfer is valid on the ledger, the transfer is always accepted" is R3, a `given`: it claims nothing at all for invalid transfers (`Core.lean:71`).
- "If a transfer is accepted, the same transfer with an amount no larger is also accepted" is the frame 12 template: every pair must answer, even when the first is rejected (`Core.lean:86`).
- The surface is the same. Only the category of the "If" clause (condition or answer class) tells them apart.

**B3. "No aliases" is not true of this proposal.**
- Rows 1 and 5 leave out the R2 marker. With it, row 5 would read "If a transfer, accepted or rejected, is accepted, …".
- "If a X {class}" does not fit the existing class forms, which are whole clauses: "it is accepted" and "there is a result" (`clausebook.yaml:395`, `:406`), and "the operation succeeds" (`:231`). Frame 12 on a lookup would read "If a lookup there is a result".
- Each class would need a second, predicate form beside its Then form. That is the aliases' class P under another name.

**B4. Frame 14 plus narrowing.** "A rejected transfer and the same transfer with an amount no smaller give the same answer" reads as the substantive frame-16 rule (`:98`) and is vacuous (2.1). R2 does not refuse narrowing for frames 12, 14 or 16.

**B5. The sentence loses "on the same ledger".** "the same transfer with an amount no larger" omits the condition `s₂ = s` (`Pieces.lean:80-81`), which the current printed reading states (`clausebook.yaml:421`). "If accepted, the same transfer is also accepted" then reads as a sequence on the ledger the first call left, which is a false claim.

**B6. Frame 13's new wording borrows frame 14's head.** "gives the same answer and leaves the same ledger as R" begins like "gives the same answer when V" (`clausebook.yaml:965`). Its " and " also meets `and_splits` (`vocab.py:1220`).

**B7. R3 plus the article rule** puts the operation's first mention inside a quantifier. Row 7's "If no transfer of a batch is valid" can be read as "no transfer of any batch".

**B8. R5 keeps the "For" voice for frames 9-result, 10-result, 11 and 15.** The faulty narrowing form from 2.2 survives there: "For a batch, if it is rejected, the number of transfers applied is zero" compiles to `ResultIs (L.applyBatch).rejected …` (`probe_c.out`).

**B9. R1 is incomplete.** It misses "the operation succeeds" and the 2.3 pairs.

**B10. The family guard fires on noise.** "Any family worse by more than 5 points keeps its current forms" fires **24% to 75%** of the time with no real difference (4 families, 24 to 96 judgements each, error 5% to 20%).

**B11. Contamination.** By regex over `trials/sentences/authors.json`: 5 of the 48 frozen sentences open with If, When, Whenever or Given; 3 say "accepted or rejected" or "whether … accepted/rejected"; 5 use "accepted" as an adjective; none uses "successful". R1, R2 and R3 coincide with up to 13 of them (overlap not computed). Any L4(a) gain there is contaminated.

## 5. Layers

**Verified:** findings 1, 2, 3, 5, 6 and 8 (`clausal/clausal/core.py:114-122`, `:241`). Finding 4 is right that the echo is a deterministic function of the parse tree, but that does not make it faithful (2.2).

**C1. The gloss would write the wrong lines from 2.2 into the file.**
- The proposal builds the gloss from `echo_rule`.
- For "For a lookup, if it is accepted, …" it would print "covers every call; must answer [D1 D2]" beside a statement that covers accepted calls only and requires no answer.
- For any narrowed two-run rule it would print "both must answer [D10]".
- The byte-for-byte comparison on each compile pins the wrong text instead of catching it.
- The claim that its "templates sit inside the signed piece digest" is false for these lines (2.2).

**C2. A table built from `flat` would overstate narrowed rules.**
- D2 is specified as the truth table of the frame's `flat`, and `flat` for frame 12 is `{c} → {c2}` (`clausebook.yaml:944`). It carries neither the calls guard nor the requirement to answer, yet T1's own table has a "no answer" row.
- Built from `flat`, the table for "A successful transfer never loses acceptance when the amount is larger" shows "accepted then rejected: forbidden", which the Lean does not forbid.
- Built from `.at` or `Check.observe` (`Check.lean:24-42`), D2 is the only element in all three proposals that would show a vacuous narrowing to a reader.

**C3. T1's "= silent when run 1 is rejected" is false.** Run 2 must still answer.

**C4. The hand-worked gloss already has an error.** R4 tags D9 on "some … is not valid", but the compiler applies D9 only to `every` or `every_of` with "not" (`vocab.py:1178`).

**C5. Runner labels collapse.**
- Gherkin's Rule name is its first line (`core.py:178-189`; the gherkin `Rule` struct per `out/prior_art_vocabulary.md:167`). With breaks after the subject, every key-release rule is reported as "A key release".
- The current parser drops blank lines and indentation (`core.py:175-180`), so the layout rules need a new parser. No current Rule line ends in a full stop.

**C6. The sentence does not change.** The owner asked for better sentences. Layers fixes none of the bad wording except README corrections, and does not meet "defaults written out in the sentence" (`docs/PLAN.md:41`).

**C7. The trial measures lookup more than reading.**
- Arm D shows cases of the same trap kinds the items test. T1's table answers the no-answer item directly.
- "Helped" needs a drop of at least 10 points. From a proxy error near 8% (`RESULTS.md:81`) that is unreachable unless these trap kinds start at 20% error or more.

**The conflicts:**
- In a combined grammar, "If a transfer is rejected, …" would carry three meanings:
  - narrowing (aliases row 5);
  - a first-run condition with both calls required to answer (reshape frame 16);
  - a scope that claims nothing outside it, when a condition follows (reshape R3).
- The slot just after the subject would mean frame 16's condition in aliases and a coverage marker in reshape.

**Order I recommend:**
1. The 2.1 refusal and the 2.2 print fix.
2. The surviving items in the table, before C1 and H1.
3. Only then a fronted or positional form, gated by a people trial on dropped-condition and narrowing items, with a "hurt" decision based on a confidence interval rather than a point threshold.
