# Tool improvements, ranked by what they would unlock in the census corpus

Generated by `scripts/tables.py`; edit `scripts/IMPROVEMENTS.template.md`. Source read: Charon at `454586e9` and Aeneas at `5a392f4b` (the pinned commits), cloned read-only into `census/upstream/`. Line numbers refer to those commits.

**Purpose.** Input for deciding whether to fork a tool or contribute upstream. This document reports what each change would unlock here, where it would go and roughly what it would take. It does not recommend.

## How the ranking is computed

- **Unit.** Functions and code lines of the ten-crate census (`CENSUS.md`), in the "peeled" runs.
- **Lower bound ("unlocked").** Functions whose failure messages all fall in the cause classes the improvement addresses. Fixing it should make these compile, unless a second problem is hiding behind the first: the tools stop at the first error in a function.
- **Upper bound ("appears in").** Functions in which those classes appear at all.
- **The two whole-crate rows** (`abort`, `ice`) count the functions that compile in the peeled runs of the crates that give nothing as shipped. The peel is an emulation of the fix, so these are measured, not estimated.
- **The `mixed` row is a count of messages, and the measured figure is lower.** A run that emulated the fix on cedar got about 1,560 functions past Aeneas's translation (from 37), then died elsewhere; see its note.
- **On cedar the rows depend on each other.** Nothing of cedar comes out until `ice`, `abort`, `crash` and `mixed` are all dealt with, in that order, and uncaught exceptions in the pure micro-passes come next.
- **Limits.** The corpus is ten crates and one of them is more than half of it; a class concentrated in one crate (see the last column) says more about that crate than about Rust. Effort figures are estimates from reading the code, not from trying the change. Nothing was built from source: there is no OCaml toolchain on this machine.

## What the ranking says, in one paragraph

Six of the eighteen rows, and part of a seventh, are robustness defects: one unsupported declaration makes the tool give up on a crate, or on everything after a point in it (`mixed`, `abort`, `ice`, `crash`), or the generated Lean does not compile although Aeneas reported success (`shadow`, `leanmisc`, part of `match`). They account for the top two rows and for most of the corpus, and each is small where it could be located. The rows that are Rust features Aeneas does not support (`dyn`, `borrow`, `fnitem`, `float`, `rawptr`, `loops`, `hrtb`) are smaller here and larger to build. Whether that ordering holds outside these ten crates is not something this corpus can show.

## A flag that already exists

`aeneas -filter-trait-methods` drops, from a trait impl, the methods that the Lean model of the trait does not have. Without it, every impl of a modelled trait that defines more methods than the model (`size_hint`, `count`, `nth` … on `Iterator`) is a Lean error ("`size_hint` is not a field of structure `core.iter.traits.iterator.Iterator`"). The census was run with default flags. The side run with the flag removes those errors, and the trait instances then exist; in this corpus that changes the status of no function (the functions that failed still fail for their own reasons):

## Fork or upstream: facts that bear on the choice

- **Release cadence.** Aeneas publishes a binary every night (the eight most recent releases are dated 2026-11-03 to 2026-11-10); Charon is pinned by Aeneas per commit. Two of the failure sources found here are days old: the Charon ICE comes from commits of 2026-11-07 and 2026-11-08, and hax 0.5.0, which pins Charon nightly-2026.10.31, does not have it.
- **Size of the changes.** `mixed` is one line; `abort`, `crash` and the name-capture fixes are tens of lines each, in code that already has the pattern to copy. Loops, floats and function items are contained features (one pass or one evaluator case plus library work). Trait objects are a feature of a different order.
- **Ready to report upstream.** `probes/mixed-group-probe-0.1.0` reproduces `mixed` in about 100 lines; the `Iterator::copied` and `str::find` aborts each reproduce in a one-line function (`probes/profile-probes-0.1.0`, `iters::copied_max_before`, `strings::find_char_before`). None of these was checked against the upstream issue trackers.
- **What a fork has to carry.** The Lean library (`backends/lean`) is versioned with the binary and pins Lean and Mathlib (v4.35.0 on 2026-11-09, v4.36.0-rc2 on 2026-11-10). A fork inherits that coupling and the nightly Rust pin (`nightly-2026-09-17`).
- **Build requirements.** Aeneas is OCaml (dune, opam); Charon is Rust against `rustc-dev` of one nightly. Neither was built here.
- **Models: two routes.** Aeneas's list of modelled items (`src/extract/ExtractBuiltinLean.ml`, 1,844 lines) is generated from the `@[rust_fun "…"]` attributes of its Lean library when Aeneas is built, so adding a model to that list means a rebuild: upstream or fork. The route that needs neither is `aeneas -split-files`, which writes the external declarations to a template file meant to be completed by hand (Aeneas prints this advice on every census crate). It was not tried here.
