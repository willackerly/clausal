## Method

### What is counted

- **A function** is a `fn` item with a body in the crate's own source (free functions, methods, trait impl methods, trait default methods, nested functions), found by a `syn`-based inventory (`tools/fninv`) that does not depend on Charon. Test code (`#[test]`, `#[cfg(test)]`, `tests/`, `benches/`, `examples/`) is left out.
- **Closures are not functions.** A closure belongs to the function it is written in; that function counts as translated only if all its closures do.
- **Code lines** are the non-blank, non-comment lines from the `fn` line to the closing brace; a nested function's lines are counted once, for the nested function.
- **Not compiled:** functions in modules or items that the default feature set switches off (for example `serde` support) never reach the compiler. They are listed in the corpus table and left out of every rate.
- **Functions written by derives and macros** (`#[derive(Clone)]` gives a `clone` function) are not in the inventory. Charon sees them; they are reported as a separate group and are not in the rates.

### The three stages, per function

1. **Charon extracts:** the function has a body in the LLBC file and no error flag.
2. **Aeneas translates:** every Charon declaration of the function (the function, its closures, its loops) has a Lean definition in the output; none of them is an axiom, contains a `sorry` hole, or has an error logged against it.
3. **Lean compiles:** `lake build` reports no error inside any of those definitions. Lean is run with `-DmaxErrors=10000000`, since it otherwise stops a file at 100 errors.

Three readings of success are reported, from loose to strict:

- **Lean compiles:** the function's own definitions compile. A callee that failed appears to the caller as an axiom, so this alone does not mean the function can be reasoned about.
- **Every local callee compiles:** the function and, transitively, every function of the same crate it refers to compile.
- **No unmodelled external:** in addition, nothing in that closure refers to an external item that Aeneas emitted as a Lean `axiom` because the Aeneas library has no model for it.

### "As is" and "peeled"

- **As is** is `charon cargo --preset=aeneas` followed by `aeneas -backend lean`, with nothing else done. If either tool stops without output, every function of the crate fails at that stage with that message.
- **Peeled** exists because Aeneas aborts a whole crate on one bad standard-library signature, which would make the per-function census a column of zeros.
  - *Aeneas abort:* the declaration named by the fatal error is removed from the LLBC file and Aeneas is rerun, until it finishes. For a trait method whose signature carries a trait-type constraint (`Iterator::copied`, `cloned`, `try_fold`) only that method entry is removed; for `core::str::pattern::Pattern` the trait and its impls are removed; anything else is removed as a whole declaration. A function that used a removed item then fails on its own with "could not find …", and is counted as failed with that cause.
  - *Functions under a removed trait:* when a trait goes, everything declared under its impls goes with it (Aeneas cannot print the name of an item nested in an impl that is gone). Those methods are counted as failed at Aeneas with the trait as the cause. This removes more than a real fix would, which would drop only the offending methods.
  - *Charon failure:* on `cedar-policy-core` the Charon driver triggers 49 rustc internal compiler errors. The functions containing those sites are marked `#[charon::opaque]` in a copy of the source and Charon is rerun; they count as failed at Charon.
  - *Uncaught exception in one function body* (cedar): Aeneas dies without naming the function. It is found by bisection over the function bodies, its body is made opaque, and it counts as failed at Aeneas.
  - *Cedar only, to save hours:* the two generated LALRPOP parsers are opaque for Charon, and the trait methods Aeneas aborts on are predicted from their signatures and removed up front (the prediction reproduces the one-at-a-time removals on the other nine crates).
  - *Not part of the peel:* failures that leave Aeneas running. In particular the mixed-declaration-group defect, which fails functions one by one with "Internal error", is left as it is and shows up as a cause class.
  - Every removal and mark is recorded in `data/results/<crate>.json` (`surgery`, `opaque_marks`) with the message that caused it.
- **Peeled numbers describe the tools with one kind of robustness fix applied** (skip the failing declaration instead of aborting the crate), not the tools as shipped. Both are shown everywhere.

### Failure causes

- Each failing function gets the messages logged against it: Charon's, Aeneas's (with the line of the Aeneas source that raised it, from `-print-error-emitters`) and Lean's.
- A Lean error of the form "unknown identifier X" where X is another failed definition is followed back to X's own error, so a function that fails only because a type or a callee failed is classified by the root cause.
- Messages are mapped to cause classes by the ordered rules in `scripts/report.py` (`RULES`, `EMITTER_CLASS`). A function with several different causes appears under each ("any cause"); "only cause" counts the functions for which fixing that one class would be enough.
- The classification is by message, not by reading each function. Classes named after a Rust feature rest on Aeneas's own wording or on the source line that raised the error; the catch-all classes are listed as such.

### Syntactic features

The inventory records what each function contains (loops by kind, closures, `?`, `unsafe`, trait bounds, macros called, methods called). These are used to show how functions with a given idiom fare. They are correlations within this corpus: a function with a `for` loop may fail for another reason.

### Side columns

- **Newer Aeneas (nightly-2026.11.10):** ships the same Charon; the only upstream commit in between is the move to Lean v4.36.0-rc2. The newer `aeneas` binary was run on the identical LLBC files and its output compared line by line (`scripts/compare_new.py`). Its Lean output was not compiled.
- **hax 0.5.0** (`cargo hax into lean`): since 0.4 its Lean backend is a driver around its own pinned Charon (nightly-2026.10.31) and Aeneas (build-2b9e3ea), with extra flags and its own library. Run on a copy of each crate, crate-level outcome only (`scripts/run_hax.sh`). Its generated Lean project was not built: that needs its own dependency fetch (`lake update`).

## `cedar-policy-core`: what stood in the way

Cedar is the crate the plan cares most about (node S1), and it is where the tools did worst. In order:

1. **Charon does not finish.** 49 sites trigger a rustc internal compiler error under the Charon driver (`error performing operation: fully_perform`, from Charon's recovery of user type annotations such as `collect::<Vec<_>>()`). The functions containing them were marked opaque ({{cedar_marks}} sites in {{cedar_marked_fns}} functions, {{n:classes.charon_ice.any}} of them counted; the others are test code). hax 0.5.0, which pins a Charon from 2026-10-31, does not hit this.
2. **Two generated parsers.** The LALRPOP grammars are generated at build time; with their bodies extracted, one Aeneas run was still going after about 50 minutes and 60 GB of memory. They were made opaque for Charon (`data/overrides.json`). They are not source functions and are not counted.
3. **{{cedar_n_traits}} traits and {{cedar_n_methods}} `Iterator` methods abort Aeneas** on a method signature (table below). {{cedar_n_dyn}} of the traits have `dyn` in a method signature; `miette::Diagnostic`, implemented by the crate's error types, is one of them.
4. **{{cedar_n_crash}} function bodies crash Aeneas** with an uncaught OCaml exception, which also aborts the crate and names no function. They were found by bisection (129 Aeneas runs).
5. **Then Aeneas completes, and almost nothing translates.** Cedar has 87 declaration groups that mix functions with trait impls; the first, early in its declaration order, is the eleven `Display` impls of the concrete syntax tree (`parser::fmt`) and their `fmt` functions, which call each other. Aeneas's function analysis stops there, and every function after it fails with "Internal error: please file an issue": {{n:classes.mixed_group.by_crate.cedar-policy-core}} of the counted functions. This is the reported cedar figure.
6. **One step further, not in the reported figures.** With those groups moved to the end of the order (emulating a one-line fix), {{cedar_mixed_noerr}} of {{cedar_mixed_cands}} candidate functions logged no Aeneas error. The run then died in a pure micro-pass with uncaught exceptions in many functions and wrote no Lean. Isolating them was not going to finish in the time available.

- **Reproduced in 100 lines.** `probes/mixed-group-probe`: two types whose `Display` impls use each other; {{mixed_probe_before_ok}} functions compile, and every function declared after the pair fails with the same "Internal error". With the recursion moved to inherent methods (`probes/mixed-group-fixed-probe`): {{mixed_probe_after_ok}}. See rule 0 of `PROFILE.md`.
- **Reading.** Cedar's low figure is five robustness failures stacked on each other, not five hundred unsupported idioms. What its real ceiling is with those fixed was not measured; step 6 gives an upper bound for the Aeneas stage only.
- **Consequence for S1.** As shipped, nothing of cedar reaches Lean, the evaluator and authorizer included.

## Rewrite cost

**Which cause.** The most common cause overall is the mixed declaration group ({{cls:mixed_group}}). It can be rewritten away, and a probe shows how (rule 0 of `PROFILE.md`), but in cedar that means restructuring 87 groups of trait impls across the crate, not five functions; it was not attempted. The next, traits removed in the peel ({{cls:trait_removed}}), is a tool defect. Among the causes an author can remove function by function, the most common as an only cause is name capture in the generated Lean ({{cls:lean_shadow}}, class `lean_shadow`); it was also the most common cause of all in the nine crates that had finished when the experiment was fixed. Cedar functions were not rewritten: one cedar run takes about ten minutes on a quiet machine and took up to an hour on this one for most of the night. The cause has two forms: a type whose name is an Aeneas builtin (`Slice`), and a local name equal to a module name.

**Which functions.** One per distinct instance of the cause, taking the first affected function in file order: the `Slice` type of `untrusted`, the two `Slice` types of `indexmap` (map and set), and the first two module-name collisions in `time`. Rewrites 6 to 9 are extras for two other source-level causes where the rewrite changes code instead of names: loop exits (6, 7) and a method passed by name (8, 9; class `fn_ptr`, {{cls:fn_ptr}}).

**Procedure** (`rewrites/run.py`): apply the patch in `rewrites/patches/` to a copy of the pinned crate, run the crate's own tests on the pinned and the patched source, run the whole census pipeline on the patched crate, and read the function's status before and after.

{{rewrites}}

- **All five (rewrites 1 to 5) translate and compile after the rewrite, and the crates' tests give the same result as before.** The patches change 2 to 9 lines and no logic. The four extras do too.
- **A rename fixes more than its function.** One five-line patch to `indexmap` (rename the struct, keep `Slice` as a type alias, re-export the new name) takes the crate from {{n:rw.3.crate_ok_before}} to {{n:rw.3.crate_ok_after}} compiling functions; the nine-line rename in `untrusted` from {{n:rw.1.crate_ok_before}} to {{n:rw.1.crate_ok_after}}.
- **The first attempt at the `indexmap` rename did not build**: the crate denies public types that cannot be named, so the new struct name had to be re-exported. A rename in a published crate is an API decision, not only a local edit.
- **Loop exits cost more** (rewrites 6 and 7): 31 and 42 changed lines, a helper function each, and the functions grow. Rewrite 6 needed two attempts: with the loops rewritten in place, the early-exit error was replaced by a borrow error, because the loop still read through `&Params`, a struct that holds a reference; passing the two fields to a helper fixed it (`rewrites/attempts/6_attempt1.patch` is the first attempt). The second error was only visible once the first was gone.
- **A method passed by name** (rewrites 8 and 9): `.map(Bucket::refs)` written as a `match`, five changed lines each; both functions compile afterwards.
- **Tests used.** `untrusted`, `indexmap`, `shlex`: `cargo test`. `rusty-money`: `cargo test` with `CARGO_HUSKY_DONT_INSTALL_HOOKS=true` (a dev-dependency tries to install git hooks). `time`: the published crate's integration tests do not compile, pinned source included, so its 448 documentation tests were run (`cargo test --doc --all-features`); the doc test of `to_iso_week_date` is among them, `raw_to_bits` is private and is exercised only indirectly.
- **Not shown by this experiment:** the cost of rewriting for the causes that are not naming or loop shape (trait objects, borrow patterns, floats); those change a design, not a function.

## Limits of this census

- **Ten crates, one of them more than half the functions.** `cedar-policy-core` has {{n:crates.cedar-policy-core.fns}} of the {{n:overall.fns}} counted functions. The overall rate is close to cedar's rate; the "without cedar" line and the per-crate rows are there for that reason. Nothing here estimates a rate for Rust code at large.
- **Default features only.** {{n:overall.not_compiled}} source functions never reached the compiler (optional `serde`, `rayon`, formatting and parsing modules, and so on). The optional parts of a crate are often the ones with more strings, I/O and trait objects.
- **Peeled is not shipped.** The peeled figures need a change to Aeneas (or the LLBC surgery in `scripts/census.py`). As shipped, six crates give nothing.
- **First error only.** Each tool stops at the first problem in a function. A function counted under one cause may hit another once the first is fixed, so "only cause" counts are an upper bound on what a fix yields and a lower bound on what remains.
- **"Compiles" is not "correct".** Nothing here checks that the Lean model computes what the Rust computes; that is the job of the differential tests in the slice, and none were run on these crates.
- **Causes are assigned by message.** The rules are in `scripts/report.py`. {{n:classes.aeneas_internal.any}} functions carry only an anonymous internal error and {{n:classes.lean_other.any}} only an unclassified Lean error.
- **Macro- and derive-generated functions** are identified by span and kept out of the rates; their own success is in the last column of the corpus table's source, `data/summary.json` (`generated_fns`, `generated_ok`).
- **Closures share their parent's fate; nested functions are counted separately.** Line counts are of non-blank, non-comment lines and include the signature.
- **Side columns are shallow.** The newer Aeneas was diffed, not compiled. hax was run at crate level and its Lean project not built.
- **One run, one machine, and the machine was busy** (load average above 100 on 18 cores from other work during most runs). Times in the tables show order of magnitude only.
