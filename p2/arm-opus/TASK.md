# P2 proof-writing task (frozen 2026-11-10)

Plan node P2 (`docs/PLAN.md`, Track P): *an agent can write loop proofs unaided, at bounded cost.* Two
agents attempt this same task independently. This file, `SCENARIOS.tsv` and everything listed in
`FROZEN.sha256` were written by a third agent, the author, who wrote no proof.

## What to prove

`inventory/src/lib.rs` is a 161-line Rust crate: a warehouse of storage bins (`Vec<Bin>`, each bin holding
units of one product) with seven public functions that contain loops: `stock_of`, `find_bin`, `restock`,
`take`, `fill_orders`, `product_count` and `dominant_product`. Charon and Aeneas translate it to
`lean/Generated/Inventory.lean`.

`features/inventory.feature` states 7 Rules, one per function, with 16 universally quantified scenarios
beneath them (2 or 3 per function). `./run.sh` turns each scenario into a Lean statement
`Spec.inventory.<scenario>.stmt` in `lean/Spec/Statements.lean`, about the Aeneas model of the function.
The English phrases are bound to Lean definitions in `lean/Vocab/Inventory.lean` through `glossary.yaml`.

**Your job: prove all 16 statements.** Each has a proof file holding a `sorry` stub:

    lean/Spec/Proofs/inventory/<scenario>.lean      theorem Spec.inventory.<scenario> : Spec.inventory.<scenario>.stmt

`SCENARIOS.tsv` lists, per scenario, the Rust function, the Lean model function, the proof file and the
line in the feature file:

| Function | Scenarios |
|---|---|
| `stock_of` | `stock_is_sum`, `stock_too_big` |
| `find_bin` | `find_first_bin`, `find_no_bin` |
| `restock` | `restock_adds`, `restock_counts` |
| `take` | `take_amount`, `take_stock_down`, `take_earliest_first` |
| `fill_orders` | `fill_count`, `fill_state`, `fill_at_most` |
| `product_count` | `count_products`, `count_at_most_bins` |
| `dominant_product` | `dominant_found`, `dominant_none` |

Results are counted **per function**. A function is fully proved when every scenario of it is
PROVED-FOR-ALL in the report of `./run.sh`.

There is **no lemma library**. Every loop invariant, helper lemma and fact about the Aeneas library that
you need, you find and prove yourself.

The 16 statements are believed true. Before the freeze each one was checked, with no failure, on its
Examples rows (46 rows, on the compiled Rust and on the Lean model), on the pipeline's boundary grid,
on 1,000,000 random inputs against the compiled Rust and on 30,000 random inputs against the Lean model.
That is testing, not proof. If you come to believe a statement is false, say so in your report and give
the input. Do not change the statement.

`lean/Vocab/Inventory.lean` contains three small **reference definitions** (`stockIn`/`stock`, `takeFrom`,
`fillFrom`). They are listed at the top of that file. They state what some loops should compute, so that a
scenario can state an exact result. They are part of the specification, are frozen like the rest of it,
and say nothing about how to prove anything.

## Where your files go

- **Proofs**: replace the `sorry` in each `lean/Spec/Proofs/inventory/<scenario>.lean`. Keep the theorem's
  name and its type line exactly as they are. You may add `import` lines and anything you like above the
  theorem.
- **Helper lemmas and invariants**: new modules under `lean/Lemmas/` (library `Lemmas`, built by
  `lake build`), e.g. `lean/Lemmas/Foo.lean`, imported from a proof file with `import Lemmas.Foo`. Several
  proofs may share one module. If a `Lemmas` module does not compile, every proof that imports it,
  directly or not, is reported as lost; other proofs are unaffected.
- Nothing else. In particular, do not create files in `lean/Spec/` outside `Proofs/`, and do not create
  files in `lean/Vocab/`, `lean/Generated/` or `lean/Bdd/`.

## What counts as a proof

The audit that `./run.sh` runs counts a theorem as a proof only if all of these hold:

- it is named exactly `Spec.inventory.<scenario>` and its type is exactly `Spec.inventory.<scenario>.stmt`;
- it is declared in its own proof module `Spec.Proofs.inventory.<scenario>`;
- it depends on no axiom beyond `propext`, `Classical.choice` and `Quot.sound`. So no `sorry`, no
  `native_decide` and no new `axiom` anywhere it depends on;
- the derived satisfiability theorem `<id>.sat` (generated by the pipeline; it already checks for all 16)
  holds.

## The rule: the specification is frozen

You may **not** edit anything listed in `FROZEN.sha256`: the Rust crate, its unit tests, the feature file,
`glossary.yaml`, `lean/Vocab/Inventory.lean`, the second reading in `bdd/`, the generated statements, checks
and model, the pipeline (`slicegen/`, `run.sh`, `translate.sh`, `lakebuild.sh`, `lean/Bdd/`, the
lakefile, the manifest, the toolchain file), this file and `SCENARIOS.tsv`. Before you finish, run

    shasum -a 256 -c FROZEN.sha256

and every line must say `OK`. `./run.sh` regenerates the statements, checks and model from the frozen
inputs, so an edit to a generated file would not survive a run anyway.

Also: never run `lake update` and never edit `lean-toolchain`, `lake-manifest.json` or `lakefile.toml`.
`.tools` and `lean/.lake/packages` are symlinks to caches that other agents share: do not write to them or
delete them. Never build in the repository root or in `corpora/`.

## How to work

1. **Make your own working copy** and work only there. The person or agent who launched you names its
   directory; under `p2/` is the usual place (e.g. `/Users/will/dev/lean-rosette/p2/<your-arm>`):

       /Users/will/dev/lean-rosette/p2/base/workcopy.sh /Users/will/dev/lean-rosette/p2/<your-arm>
       cd /Users/will/dev/lean-rosette/p2/<your-arm>

   The copy takes a few seconds and starts warm.
2. In every shell: `export PATH="$HOME/.elan/bin:$HOME/.cargo/bin:$PATH"`.
3. **Build one scenario** (and whatever it imports, including your `Lemmas` modules):

       ./lakebuild.sh Spec.Proofs.inventory.<scenario>
       NOTE="what this attempt tries" ./lakebuild.sh Lemmas.Foo Spec.Proofs.inventory.<scenario>

   This is a warm `lake build` of those modules, a few seconds plus the time your own proof takes. It
   prints errors and `sorry` warnings.
4. **Get the verdicts**: `./run.sh --no-rust --no-adequacy` (faster) or `./run.sh` (everything, about 20 s
   warm). A proved scenario shows as `PROVED-FOR-ALL`; the full report is `out/report.md`. `run.sh`
   exits 0 only when every scenario is proved. It deletes and recreates `out/`.

**Every build attempt goes through `./lakebuild.sh`.** It appends one line per call to
`effort/attempts.tsv`: UTC time, targets, ok or FAILED, seconds, number of error lines, and your `NOTE`.
That file is how the cost of the proofs is measured: failed builds count. Do not edit it, do not build
proof or lemma modules any other way (no plain `lake build`, no `lake env lean` per check), and do not
use an editor or language server that compiles them for you outside this log. `./run.sh` runs its own
builds; those are not attempts and are not logged.

## Independence

- Do not read or copy from other working copies under `p2/`, or from `slice/`. `slice/` holds proofs about
  a different crate and is being restructured by another agent.
- You may read the Aeneas Lean library (`.tools/aeneas-nightly-2026.11.09-5a392f4/backends/lean/`), Mathlib
  and Lean's own sources, and this directory's `DESIGN.md` and `TOOLCHAIN.md`. Those two describe the
  pipeline as it was built for two earlier fixtures, a wallet and a ledger, which are not in this copy.
- The budget for your attempt (tokens, wall-clock) is set by whoever launches you and should be written
  down before you start.

## What to report when you stop

Per function: fully proved or not, and for each scenario its verdict from `./run.sh`. Also give the output of
`python3 effort/count.py` (hand-written Lean lines against Rust code lines), the number of lines and of FAILED
lines in `effort/attempts.tsv`, the wall-clock time from your first to your last attempt, the result of
`shasum -a 256 -c FROZEN.sha256`, and anything you believe to be false or unprovable as stated, with the
reason.
